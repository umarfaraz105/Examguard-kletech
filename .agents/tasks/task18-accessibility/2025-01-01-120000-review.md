# Error Boundary System for ExamGuard

Comprehensive error handling infrastructure with React error boundaries, Next.js error pages, and centralized error management system.

The implementation establishes a three-tier error boundary hierarchy (Global, Route, Component) with variants of ErrorFallback UI appropriate to each context. ErrorHandler singleton categorizes errors from Axios responses, distinguishing network failures from HTTP 401/403/404/422/5xx, and integrates cleanly with the existing toast notification system through useErrorHandler. Next.js error.tsx and not-found.tsx follow App Router conventions. TypeScript compilation and ESLint checks pass for all Task #18 files.

**Watch for:** Toast import dependency creates tight coupling between error handler and notification system (**likely**). ErrorHandler logs to console in production which may expose error details (**confirmed**). No test coverage for error boundaries or error categorization logic (**confirmed**).

**Verdict**: APPROVED

## High-level view

GlobalErrorBoundary wraps the entire application in layout.tsx and provides restart and dashboard navigation options. The three-tier hierarchy (Global, Route, Component) allows errors to be caught at the appropriate scope with UI variants that scale from full-page to inline. ErrorHandler categorizes all HTTP status codes and network errors into ErrorType enum values, with Axios interceptor integration in api.ts that processes errors before rejection. The useErrorHandler hook bridges error processing and toast notifications but creates a dependency on the toast module. Next.js error.tsx and not-found.tsx provide custom error pages with development-mode diagnostics. No circular imports exist between error modules and api.ts. Production error messages hide technical details except for console logging in error-handler.ts.

## Three-tier error boundary hierarchy

GlobalErrorBoundary is a class component at the root of layout.tsx, wrapping AuthProvider, NotificationProvider, HelpProvider, and AppLayout. It catches all unhandled errors in the React tree and renders a full-screen fallback with restart and dashboard options. Error details (message, stack, component stack) appear in development mode inside a collapsible `<details>` element.

RouteErrorBoundary uses react-error-boundary library and renders ErrorFallback with variant='route'. ComponentErrorBoundary uses variant='component'.

ErrorFallback component implements three visual variants:
- **page**: full-screen centered card with large icon (min-h-screen)
- **route**: page-sized card (min-h-[60vh]) with back button
- **component**: inline alert box (bg-error-50 border) with truncated error message

All variants conditionally show error.message in development and hide it in production.

## ErrorHandler categorization

ErrorHandler is a singleton that processes errors through `categorizeError`. For Axios errors, it maps HTTP status codes:
- No response: NETWORK
- 401: AUTHENTICATION ("Session expired. Please log in again.")
- 403: AUTHORIZATION ("You do not have permission...")
- 404: CLIENT ("The requested resource was not found.")
- 400/422: VALIDATION ("Invalid data. Please check your input.")
- 5xx: SERVER ("Server error. Please try again later.")
- Other: UNKNOWN

TypeError with 'fetch' or 'Failed to fetch' in message maps to NETWORK. Error objects without Axios structure map to UNKNOWN. String errors are wrapped in UNKNOWN AppError.

## api.ts integration

api.ts response interceptor catches Axios errors, checks for 401 status to clear token and redirect to /login, then passes the error through ErrorHandler.getInstance().handleError(). The AppError is re-thrown so callers receive typed errors instead of raw Axios errors.

```typescript
api.interceptors.response.use(
  (response) => response,
  (error: AxiosError) => {
    if (error.response?.status === 401) {
      localStorage.removeItem('access_token');
      if (typeof window !== 'undefined') {
        window.location.href = '/login';
      }
    }
    
    const appError = ErrorHandler.getInstance().handleError(error, {
      endpoint: error.config?.url,
      method: error.config?.method,
    });
    
    return Promise.reject(appError);
  }
);
```

## useErrorHandler hook

useErrorHandler provides handleError and clearError functions plus error state and isError boolean. handleError calls ErrorHandler.getInstance().handleError(), stores the AppError in local state, and displays a toast with appError.userMessage.

The toast import (`import { toast } from '@/lib/toast';`) couples error handling to the notification system. If toast module is unavailable or changes signature, useErrorHandler breaks.

## Next.js error pages

error.tsx is marked 'use client' per Next.js App Router requirements. It receives error and reset props, logs error in development useEffect, and renders a Card with AlertTriangle icon. Development mode shows error.message and error.digest in a code block. Production shows generic "We encountered an unexpected error" text. Buttons offer "Try Again" (calls reset) and "Go to Dashboard".

not-found.tsx is also 'use client'. It renders a 404 page with Search icon. Navigation buttons go to dashboard or call router.back(). Apostrophes are escaped as &apos; (ESLint fix documented in verification note).

## Error types and type guards

error-types.ts defines ErrorType enum with 7 categories (NETWORK, AUTHENTICATION, AUTHORIZATION, VALIDATION, SERVER, CLIENT, UNKNOWN). AppError interface includes type, message, userMessage, statusCode, originalError, context, timestamp. ApiError extends AppError with endpoint and method fields.

Type guards isNetworkError, isAuthError, isValidationError check error.type. isAppError checks for required properties (type, message, userMessage, timestamp).

## Accessibility and ARIA

ErrorFallback buttons have aria-label attributes and min-h-[44px] for touch targets. Icons have aria-hidden="true".

Missing: aria-live regions or role="alert" on error containers. When an error boundary triggers dynamically (after user interaction), screen readers won't announce the error unless the user manually navigates to it. Adding role="alert" to the outermost error container div would fix this.

## Sensitive data exposure

userMessage strings are generic and safe ("Session expired. Please log in again.", "Server error. Please try again later."). error.message is only shown in development mode. error.stack and errorInfo.componentStack are only rendered in development.

Production mode in error-handler.ts does log to console:
```typescript
console.error('[Error]', error.type, error.message);
```
This exposes error types and technical messages to browser console in production, which could leak details about backend implementation or validation rules.

## Missing test coverage

None of the following have tests:
- GlobalErrorBoundary catching and rendering errors
- RouteErrorBoundary and ComponentErrorBoundary integration
- ErrorHandler.categorizeError edge cases (missing response.status, malformed error objects)
- useErrorHandler hook (handleError, clearError, state management)
- error.tsx and not-found.tsx rendering

Edge cases like Axios errors with missing config, TypeError messages without 'fetch', or errors thrown during ErrorFallback rendering are not covered.
